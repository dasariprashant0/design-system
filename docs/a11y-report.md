# Accessibility tree report

> Generated by `npm run ax` (scripts/ax). Do not edit by hand: change `scripts/ax/expectations.mjs` and run it again.

## What this is, and what it is not

**This is an accessibility-tree check. It is not a screen reader test.** No NVDA, JAWS, VoiceOver or TalkBack testing has been done on Monoline, by anyone, yet. Nobody has listened to these components.

What the check does: it opens the built docs site in real Chrome, performs real key presses and clicks, reads the full accessibility tree that Chrome builds from the page (the same tree screen readers on Windows, macOS and Android read, through `Accessibility.getFullAXTree`), and asserts roles, names, states, relationships, focus and live regions against the expectations in `scripts/ax/expectations.mjs`.

What it cannot tell you: how a given screen reader words those things, whether the order and amount of speech is pleasant, whether a flow makes sense without sight, how virtual cursor and focus modes behave, how Safari or Firefox build their own trees, or anything about touch screen readers. The "expected announcement" below is built from the tree with a fixed template (name, role, state, then description). NVDA, JAWS and VoiceOver each word it differently. Treat it as what the tree says, not what you will hear.

## Summary

- Components and examples checked: **41**, plus the docs page landmarks and heading order.
- Checks that fail: **0**. Open findings that are understood and not fixed: **9**.
- Problems found and fixed in components while building this check: **5 groups** (listed below).
- Generic checks on every example: every control has a role and a non-empty name; no focusable element with no role ("generic"); `aria-labelledby` and `aria-describedby` resolve to text; an invalid field says why; every dialog has a name, a description (unless noted) and reports modal, and nothing outside it stays in the tree.
- Chrome does not surface `aria-current` or `aria-sort` in the tree through this protocol; those are read from the DOM and marked as such.

## Fixed because of this check

- **accordion, select, combobox, multi-select, tree-select, breadcrumb.** CSS generated content ("+", "−", "↓", "✓", "/") was part of the accessible name or value, so a screen reader would read "What is Monoline? minus" or "15 minutes down arrow". The glyphs now have empty alternative text (`content: "+" / ""`), so they stay visible and are not announced.
- **dialog, alert-dialog, drawer, command.** The dialog did not report itself as modal (`aria-modal`). The page behind was hidden by Radix, but not every assistive technology relies on that. `aria-modal="true"` is now set on the content and can still be overridden through props.
- **carousel.** The scrollable slide track was a focusable `div` with a label and no role, which Chrome exposes with no role ("generic"). It is now `role="group"`, so focus announces "Featured slides, group".
- **combobox.** The suggestion list had no name unless `aria-label` was passed, so inside a `Field` it was announced as just "list box". It now takes its name from the input.
- **context-menu (docs example).** The menu had no accessible name. The example now passes `aria-label`; any real use needs one too.

## What the owner should test by hand

Run these on real hardware or a real machine, with each assistive technology below, against the docs site or a page built from the components. Record what was said, not whether it "worked". Fifteen flows, in order of how much damage a failure would do:

1. **Skip link, landmarks and headings.** Reach the main content with the skip link, then list landmarks and headings. Expect one main, a named navigation, headings that do not skip a level.
2. **Button, icon button and a disabled button.** Tab to each and listen to name, role and state. A loading button should say it is busy.
3. **A text field with a hint and an error (Field).** Tab into the field, then submit it invalid. Expect label, then hint, then the error read with the field, and the error announced when it appears.
4. **Checkbox, radio group and switch.** Toggle each with Space; arrow through the radio group. Expect checked, not checked, and the group name.
5. **Select and combobox.** Open each with the keyboard, move through options, choose one. Expect the options, the selected state, and the chosen value read back.
6. **Tabs.** Arrow between tabs. Expect "selected", the tab count, and the panel name when you leave the tablist.
7. **Accordion.** Open and close an item with Enter. Expect expanded or collapsed, and no stray "plus" or "minus".
8. **Dialog and alert dialog.** Open from the trigger. Expect the title and description read once, focus inside, the page behind unreachable, and focus back on the trigger after Escape.
9. **Dropdown menu, menubar and context menu.** Open with Enter, Space and the context key. Expect menu name, item names, arrow navigation, Escape returning focus.
10. **Popover, tooltip and drawer.** Open each. The tooltip text should be read as a description of the control; the drawer behaves like a dialog.
11. **Toast and status messages.** Trigger a toast and a data table sort without moving focus. Expect the text to be spoken once, politely (assertive only for errors).
12. **Form with an error summary.** Submit empty. Expect the summary announced, each link jumping to its field, each invalid field reading its reason.
13. **Data table and data grid.** Sort a column, move through a grid with the arrow keys, select a row. Expect column and row headers read with each cell, sort order announced, selected state.
14. **Calendar and date picker.** Move by day, week and month, pick a date. Expect the full date read for each day, the month change announced, the chosen date read back in the field.
15. **Slider, rating, OTP input and file upload.** Adjust the slider with arrows (value read each step), rate, type a code (focus moves, each digit named), choose a file (file name announced).

### NVDA with Firefox and Chrome (Windows)

Start NVDA, open the docs site, press `Insert+Space` once to be sure browse mode is on. Browse mode: `Down` reads line by line, `Tab` jumps between controls, `D` landmarks, `H` headings, `B` buttons, `F` form fields. Turn on the Speech Viewer (NVDA menu, Tools) and copy what it says into the notes.

Run flows 1 to 15. Pay extra attention to:

- Browse mode versus focus mode: dialogs, menus, grids and the combobox should switch to focus mode on their own, and back when they close.
- Live regions: error text, toasts and the data table sort status should be spoken without moving focus.
- Name and role: compare each announcement with the "Expected announcement" column of this report.

- Safari does not support CSS alternative text before version 17.4: check that the accordion and select still do not read their glyphs on older versions.
